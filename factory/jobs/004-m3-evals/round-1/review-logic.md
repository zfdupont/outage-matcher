1. `src/outage_matcher/evals/faithfulness.py:66-67`: `cited_evidence` stops with `break` as soon as one chunk would push the total past MAX_EVIDENCE_CHARS (15000). It walks `result.evidence` in retrieval order, which is not the order the answerer used. Chunks the answer node actually used (the grader-accepted `relevant` chunks) can sit after earlier retrieved but rejected chunks of a cited document, or after the up-to-6000-char `full_document` chunk from `get_postmortem`. They are then dropped, and the judge marks claims drawn from them unsupported because the excerpt is missing. The `break` also discards smaller chunks that would still fit. This biases the headline faithfulness number downward by an amount that depends on retrieval order. Fix: use `continue` instead of `break`. Better, also order the evidence so chunks the answer saw come first. Either expose the accepted chunks on `AgentResult` (the graph has `state["relevant"][:MAX_ANSWER_CHUNKS]`), or put each cited doc's accepted chunk first. Add a test where the answer-relevant chunk comes last and the earlier chunks fill the budget. The current test (`test_cited_evidence_truncates_long_chunks_and_caps_the_total`) only checks the cap.

2. `src/outage_matcher/evals/faithfulness.py:110-117`: the retry for a bad verdict does not cover invalid JSON. `JUDGE_ATTEMPTS = 2` and the README and comment say "one retry when the verdict is not the requested JSON". But `client.chat_json` (`deepseek.py:128-133`) raises `DeepSeekError` for non-JSON or non-object replies. That exception leaves `judge_answer` on the first attempt, and only the `ValueError` from `parse_claims` is retried. A reply truncated at `max_tokens=2000` (an answer with many claims) or a malformed object therefore fails the query with no retry. `test_judge_answer_retries_once_on_a_malformed_verdict_then_gives_up` only covers valid JSON with the wrong shape. Fix: catch `DeepSeekError` inside the loop too. Retry only on the not-JSON case, since HTTP failures were already retried in `_post`. Re-raise after the last attempt, and add a test where the first reply is invalid JSON and the second is valid. Optionally raise `max_tokens` for the judge.
