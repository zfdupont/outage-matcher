1. `src/outage_matcher/evals/gate.py:112-127` and `:253` (`present_ids`). The gold id check only tests that the held-out chunk ids and relevant doc ids exist. Chunk ids are `SERIAL` and `ingest` does `TRUNCATE ... RESTART IDENTITY` (`ingest/index.py:82`, `db.py:33`). If any page changes its chunk count, every later chunk id shifts. Those ids still exist, so `gate index` passes, and `version_warning` then tells the reader "the gold ids and counts are compatible". In fact `held_out_chunk_ids` would point at the wrong chunks. The held-out root-cause chunk could then stay searchable and inflate recall and MRR, or an unrelated chunk could be excluded. The gold rows also carry the stable `held_out_ords` and `doc_id`, so this is checkable.
   Fix: in `present_ids`, select `id, postmortem_id, ord` for the gold chunk ids. Count a gold chunk as present only if its `postmortem_id` equals the gold row's `doc_id` and its `ord` is in `held_out_ords`. Report the others as missing or misaligned, which is a hard failure with the refresh message. Add a test where the ids exist but belong to another document or ord.

2. `.github/workflows/eval.yml:67-70` and `:158-161` (the "Fetch raw pages (cache miss only)" steps). `fetch-raw` exits 0 when some pages fail (`cli.py` `cmd_fetch_raw`, only `--strict` exits 1). The cache is saved when the job passes, and a few missing pages stay within the 2 percent drift, so that job passes with only a version warning. On every later run the cache key matches, the fetch step is skipped, and the missing pages are never retried. The incomplete corpus is cached permanently and the warning repeats every run. This also undermines the owner decision that a version-only change is a warning.
   Fix: run `fetch-raw` unconditionally. It already fetches only absent pages, so it costs nothing on a complete cache. Do this in both jobs. Optionally have the retrieval job fail on a failed fetch, or skip saving the cache when pages failed.
